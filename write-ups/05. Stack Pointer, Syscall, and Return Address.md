#### What the stack actually is

Picture a stack of plates. You can only add a plate to the **top**, and you can only remove the **top** plate. You can’t grab one from the middle without taking everything above it off first. That’s exactly how the CPU’s stack works — a region of memory where you only ever add or remove from one end.

#### RSP — the stack pointer

```
RSP = Stack Pointer (64-bit)
```

RSP is a register that always holds the **memory address of the current top of the stack**. Whenever something gets added to the stack, RSP updates to point at the new top. Whenever something gets removed, RSP updates back.

One thing that confuses beginners (it confused me too): on x86_64, **the stack grows downward in memory**. “Adding” to the stack actually _decreases_ the address RSP points to, not increases it. So when you push something, RSP’s value goes _down_, even though conceptually we think of the stack “growing.”

#### Return address — why the stack matters for function calls

Remember `call` from our earlier writeups? When you `call` a function, the CPU needs to remember **where to come back to** once that function finishes. That’s exactly what gets stored on the stack:

1. `call some_function` automatically **pushes the address of the next instruction** onto the stack (this becomes the “return address”).
2. RSP moves down to point at this newly-pushed return address.
3. The function runs.
4. When the function hits `ret`, it **pops** that return address off the stack and jumps back to it — resuming exactly where it left off.

This is why the diagram above matters: before the call, RSP points at whatever was already on top. After `call`, a new slot appears — the return address — and RSP moves to point at _that_.

#### Syscall — asking the kernel for help

`syscall` is how a program asks the operating system’s kernel to do something it can’t do on its own — like exiting the program, reading a file, or writing to the screen. Programs run in “user mode” with limited power; the kernel runs in a more privileged mode. `syscall` is the doorway between the two.


```nasm
mov rax, 60    ; syscall number — 60 means "exit" on Linux
mov rdi, 0     ; first argument to the syscall — exit code 0
syscall        ; actually ask the kernel to do it
```

The pattern is always similar: put the **syscall number** in RAX, put any **arguments** in RDI/RSI/RDX (same registers used for function arguments), then execute `syscall`. The kernel takes over, does the work, and (for most syscalls, except exit) control comes back to your program afterward.
### The exit code isn’t fixed to 0 — it’s a message to whoever ran your program

`rdi` holds the **exit status** of your program, and you can put _any_ number from 0-255 there, not just 0. The number itself is a signal about _how_ your program finished:


```nasm
mov rdi, 0     ; "I finished successfully, no problems"
```



```nasm
mov rdi, 1     ; "something went wrong"
```



```nasm
mov rdi, 2     ; a different kind of error, by convention
```

### Where does this number actually go, and who reads it?

When your program exits, that number becomes available to **whatever launched your program** — usually your shell. On Linux you can check it immediately after running something


```bash
./myprogram
echo $?
```

`$?` prints the exit code your program set. This is genuinely useful in real workflows — scripts constantly check `$?` to decide “did the last command succeed or fail?” and branch accordingly (`if command; then ... else ...`).

### Why 0 specifically means “success” (the convention)

This isn’t a hardware rule — it’s a **Unix convention** that basically everything follows:

- **0 = success** — nothing went wrong.
- **Non-zero (1-255) = some kind of failure**, with the specific number sometimes meaning something specific (e.g., a program might use `1` for “generic error,” `2` for “bad arguments,” etc. — this is up to whoever wrote the program).

Why 0 for success instead of something else? Mostly historical/logical: it maps cleanly onto the idea of “zero problems happened.” It’s been the standard since early Unix, and literally every shell, every CI pipeline, every script written since then expects it.

#### How these three connect

- The **stack** is where return addresses live, so the CPU always knows “where to go back to.”
- **RSP** is just a register tracking exactly where the top of that stack currently is.
- **syscall** doesn’t use the stack directly for its arguments (it uses registers, like we saw with RAX/RDI) — but the stack is still what makes it possible for your program to return control properly after a function call leads up to that syscal
