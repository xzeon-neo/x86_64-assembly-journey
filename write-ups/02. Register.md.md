Okay, so last time we figured out 8-bit (AL, AH) and 16-bit (AX) registers. Now let's go one level up: **32-bit registers**.

The pattern repeats itself, but with a twist. Instead of being made of two smaller pieces (like AX = AL + AH), the 32-bit register is just the 16-bit register **extended**.

```
EAX = 32 bits
```

The "E" in EAX stands for **Extended**. So:

```
EAX ---------------------> 32 bits (whole thing)
 └── AX ------------------> lower 16 bits
      └── AL / AH --------> lower 8 bits / next 8 bits
```

Unlike AX (which splits cleanly into AL and AH), there's **no "upper half" name** for the top 16 bits of EAX. You can't say "EAH" — that register doesn't exist. If you want the upper 16 bits of EAX, you have to shift/mask for it; there's no shortcut name like there was for AH.

Same naming pattern applies across the board:

|32-bit|16-bit|8-bit (low)|8-bit (high)|
|---|---|---|---|
|EAX|AX|AL|AH|
|EBX|BX|BL|BH|
|ECX|CX|CL|CH|
|EDX|DX|DL|DH|

#### Pseudo code

```
MOV EAX, 0x12345678
```

This puts the full 32-bit value into EAX. Break it down:

- lower 16 bits (AX) = 0x5678
- of which, AL = 0x78, AH = 0x56
- the upper 16 bits (0x1234) have no name — they're just "part of EAX"

So changing AL or AX still works exactly like before, it just now affects a small slice of a bigger register.

**One quirk worth noting now** (we'll see why it matters when we hit 64-bit): on x86_64, if you write to a 32-bit register like EAX, the CPU automatically zeroes out the upper 32 bits of the full 64-bit register (RAX). This doesn't happen with 8-bit or 16-bit writes — only 32-bit writes have this "auto-zero the rest" behavior. Keep that in your back pocket, it trips people up constantly in real disassembly.

### 03. 64-bit Registers

Now the main event, since we're doing x86_**64** — the 64-bit registers.

Same extension pattern again:

```
RAX ---------------------> 64 bits (whole thing)
 └── EAX -----------------> lower 32 bits
      └── AX -------------> lower 16 bits
           └── AL / AH ---> lower 8 bits / next 8 bits
```

The "R" in RAX stands for **Register** (sometimes people just think of it as "the 64-bit version"). Same deal as before — there's no name for the upper 32 bits of RAX on their own.

|64-bit|32-bit|16-bit|8-bit (low)|8-bit (high)|
|---|---|---|---|---|
|RAX|EAX|AX|AL|AH|
|RBX|EBX|BX|BL|BH|
|RCX|ECX|CX|CL|CH|
|RDX|EDX|DX|DL|DH|

#### The "extra" registers

x86_64 also added 8 brand new general-purpose registers that didn't exist in 32-bit x86: **R8 through R15**. These don't follow the AL/AH-style naming (since they're new, there was no legacy name to build on) — instead they just get a size suffix:

|64-bit|32-bit|16-bit|8-bit|
|---|---|---|---|
|R8|R8D|R8W|R8B|
|R9|R9D|R9W|R9B|
|...|...|...|...|
|R15|R15D|R15W|R15B|

(D = Doubleword/32-bit, W = Word/16-bit, B = Byte/8-bit)

#### Pseudo code

```
MOV RAX, 0x1122334455667788
```

- lower 32 bits (EAX) = 0x55667788
- lower 16 bits (AX) = 0x7788
- AL = 0x88, AH = 0x77
- upper 32 bits (0x11223344) = no name, just "the rest of RAX"

#### Why this matters for later (RE preview)

You'll see RAX/RDI/RSI etc. constantly once we get to function calls — these are exactly the registers used to pass arguments and return values (we already touched this in the `_sum` function example). So getting genuinely comfortable with "which register is secretly a slice of which bigger register" now will save you a lot of confusion reading real disassembly later, where a compiler might use EAX in one line and RAX two lines down for what looks like "the same" value.
